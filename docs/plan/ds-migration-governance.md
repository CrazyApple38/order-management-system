# DS移行 ガバナンス文書（役割分担・テストサイクル・評価基準）

- 作成日: 2026-04-18
- 関連: [ds-migration-plan.md](./ds-migration-plan.md)
- 確定済み判断事項:
  - 着手順: **M0共通基盤 → Order Book → Screen Layout → Weekly Schedule → Quick Access**
  - 合格基準: **100点満点で70点以上、かつ重大Claimゼロ**
  - カテゴリ色: **4色相分化（D5.2）を適用**
  - WS行高: **comfortable(36px) に統一**

## 1. エージェント役割分担

| 役割                            | 略号 | 担当                                                                                       | 実装手段                              |
|--------------------------------|------|-------------------------------------------------------------------------------------------|--------------------------------------|
| **Test Designer（テスト設計者）** | TD   | フェーズ開始時に評価項目・合格基準を定義し、サイクル末尾でレポートを確認して次フェーズのテスト項目を設計 | Agent（general-purpose, 指示書型）     |
| **Implementer（実装者）**        | IM   | TDの仕様に基づきCSS/HTML/JSをリファクタ                                                    | メインエージェント + Explore/general-purpose |
| **Test Executor（テスト実施者）** | TE   | TDのテスト項目に沿ってgrep・ブラウザ動作確認・視覚確認・機能回帰を実施し、客観的な結果を収集 | Agent（general-purpose, 検証型）       |
| **Scorer（採点者）**             | SC   | TE結果を**デザイナー/カラーコーディネーター視点**で採点。100点満点、70点未満なら再修正指示 | Agent（general-purpose, 採点専用プロンプト） |

**独立性の担保**: IM / TE / SC は別エージェントとして起動し、互いの判断に引きずられない。TDのみメインスレッドから指示を出す。

## 2. 基本サイクル（1サブフェーズあたり）

```
  ┌────────────────────────────────────────────────────────────────┐
  │  START: TD がサブフェーズの評価項目・合格基準を作成（事前確定）    │
  │                              ↓                                 │
  │  [IM] 実装                                                     │
  │                              ↓                                 │
  │  [TE] テスト実施 → 結果レポート（phase-logs/<phase>-te-<n>.md） │
  │                              ↓                                 │
  │  [SC] 採点 → スコアレポート（phase-logs/<phase>-sc-<n>.md）    │
  │                              ↓                                 │
  │  合格判定: 70点以上 AND 重大Claim=0 ?                          │
  │     Yes → 次サブフェーズへ / No → TDが修正指示 → IM再実装へ     │
  └────────────────────────────────────────────────────────────────┘
```

**反復上限**: 1サブフェーズあたり最大5回。5回経過しても合格しない場合はメインエージェントがユーザーにエスカレーション。

## 3. 評価ルーブリック（100点満点）

デザイナー/カラーコーディネーター視点での採点基準。サブフェーズの性質により各カテゴリのウェイトを調整する（TDが事前に定義）。

| カテゴリ                        | 配点  | 評価内容                                                                    |
|--------------------------------|------|---------------------------------------------------------------------------|
| **A. DS準拠（トークン・命名）**  | 30   | CSS変数・クラス名が新DS（`styles-light.css` / `tokens.json`）と完全一致     |
| **B. カラーコーディネーション**  | 20   | Coastal Palette整合、コントラストAA、カテゴリ色分化、意味色の統一性          |
| **C. タイポグラフィ・余白**      | 15   | フォントスタック、`tabular-nums`、スペース・角丸・影がトークン経由             |
| **D. コンポーネント一貫性**      | 15   | ボタン・フォーム・テーブル・モーダル・バッジがDS規約通り                      |
| **E. 機能回帰（バグゼロ）**      | 10   | 既存の主要インタラクション（選択・編集・フィルタ・DnD等）が全て動作            |
| **F. アクセシビリティ**          | 5    | `aria-*` / `.sr-only` / フォーカスリング / キーボード操作                    |
| **G. コード品質・保守性**        | 5    | 重複排除・エイリアス整理・コメント・命名規約                                 |

**重大Claim（Critical）**: 以下は1件でもあれば不合格（スコア問わず）
- 既存機能の破壊（保存不能・表示不能・クリック不能など）
- Coastal Palette外の色混入
- 絵文字・Unicode記号による代用
- コントラスト比がAA未達

## 4. サブフェーズ分割（実行順）

### Phase M0（共通基盤）
- **M0-1**: `co-tokens.css` 新設、`styles-light.css` と同値のCSS変数を集約
- **M0-2**: Light時の旧→新変数エイリアス定義（`--base-page` → `var(--bg-page)` 等）
- **M0-3**: 各モックアップHTMLに `co-tokens.css` をリンク（styles-*.css より前）
- **M0-4**: フォントファミリ統合（Noto Sans JP等追加、`palt` + `tabular-nums`）
- **M0-5**: `--text-tertiary/disabled` をD6値（#5A8896 / #8BAEB9）に更新

### Phase M-A（Order Book）
- **M-A1**: OBの `:root` 変数を co-tokens.css参照に置換
- **M-A2**: OBの色・影・モーション変数を新DS名へ（旧エイリアス経由で両対応）
- **M-A3**: フォント・tabular-numsをOBに適用

### Phase M-B（Order Book）
- **M-B1**: `.md-ob-form-row` → `.md-fi-field + .md-fi-label + .md-fi-input`
- **M-B2**: フィルタドロップダウンcheckbox → `.md-fi-checkbox`
- **M-B3**: 数値入力（人数・金額）→ `.md-fi-number` + tabular-nums

### Phase M-C（Order Book）
- **M-C1**: `.md-ob-grid` → `.tbl-grid` 規約へリネーム
- **M-C2**: sticky z-index → `--z-sticky` 系に統一
- **M-C3**: 曜日色（sat/sun/night）→ `data-day` 属性化
- **M-C4**: `.md-ob-even-row` → `.tbl--zebra`、合計 → `.row--total`、空セル → `.cell--empty`
- **M-C5**: 密度モード対応（`data-density`）

### Phase M-D（Order Book）
- **M-D1**: ボタン `.md-ob-btn-*` → `.btn-*`
- **M-D2**: モーダル `.md-ob-modal*` → `.modal-*`

### Phase M-E（Order Book）
- **M-E1**: バッジ `.md-ob-badge-*` → `.chip-activated / .bt-cell-tag / .draggable-tag`

### Phase M-F（Order Book）
- **M-F1**: `aria-invalid/selected/live` 追加、`.sr-only` 導入
- **M-F2**: 印刷CSS適用

### Phase M-G（Order Book）
- **M-G1**: 旧クラス・旧変数エイリアスの削除

### Phase S-A 〜 S-G（Screen Layout、同パターン）
### Phase W-A 〜 W-G（Weekly Schedule、同パターン）
### Phase Q-A 〜 Q-G（Quick Access、同パターン）

※ 各画面個別の変形は [ds-migration-plan.md](./ds-migration-plan.md) Part 2 を参照。

## 5. テスト項目テンプレート

各サブフェーズ開始時、TDは以下のテンプレートで項目を作成する。

```markdown
# テスト項目: <Phase番号> — <サブフェーズ名>
## 目的
<このサブフェーズで達成すべきこと>

## 評価項目（ウェイト調整後の配点）
- A. DS準拠: ○点 / 30
- B. カラー: ○点 / 20
- C. タイポ・余白: ○点 / 15
- D. コンポーネント一貫性: ○点 / 15
- E. 機能回帰: ○点 / 10
- F. a11y: ○点 / 5
- G. 保守性: ○点 / 5

## Test Executor に実施させるチェックリスト
- [ ] 検証項目1（grep / 目視 / 動作手順を具体的に）
- [ ] 検証項目2
- ...

## 重大Claim判定基準
- <これに該当すれば即不合格>

## 合格条件
- 総合点 ≥ 70点 AND 重大Claim = 0
```

## 7. プロンプト規約（各エージェント用）

### TD（Test Designer）
> あなたはデザインシステム移行のテスト設計者です。新DS（`docs/ui-components/styles-light.css` + `tokens.json`）を**唯一の正**として、以下のサブフェーズの評価項目とテストチェックリストを作成してください。評価項目は上記ルーブリックに従い、**新DSに準拠した内容のみ**で構成すること。旧DSの表現・値を容認してはいけません。

### TE（Test Executor）
> あなたはテスト実施者です。以下のチェックリストに沿って **客観的事実のみ**を報告してください。grepコマンド結果、ファイル行番号、スクリーンショット相当の目視観察を記録。主観評価は行わないこと。

### SC（Scorer）
> あなたはデザイナー兼カラーコーディネーターとしての採点者です。TEの報告を基に、**ルーブリックの配点を厳密に適用**して採点してください。新DS準拠度・Coastal Palette整合・タイポグラフィの一貫性を最優先で評価。重大Claimに該当する事象があれば総合点に関わらず不合格と記載すること。

## 8. 進め方の原則

1. 各サブフェーズの最初に TD → テスト項目確定 → ユーザー承認不要（基準値は本文書で事前定義済み）
2. IM実装 → TE実施 → SC採点の3役は**必ず別エージェント**で実行
3. 不合格の場合、SC指摘を反映して IM再実装 → 同一サブフェーズのTE/SCを再実行
4. 合格したら `<phase>-summary.md` を追記して次サブフェーズへ
5. 重大な判断が必要になった場合のみユーザーに確認（AskUserQuestion）
