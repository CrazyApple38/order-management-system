# テスト戦略

受注管理システムの動作テスト戦略を定義する。
Phase 2（モックアップ）で試運用し、改善を重ねてPhase 4（本番実装）で本運用する。

---

## 1. テスト実行フロー

機能の実装が完了するたびに、以下のフローでテストを実施する。

```text
Step 1: テスト項目の導出
  Claude が要件定義・DB設計・共通テンプレートからテスト項目を導出
    ↓
Step 2: ユーザー確認項目の確定（会話）
  以下をユーザーと会話で決定する：
  ・ユーザー確認が必要な項目はどれか
  ・どの時点でユーザー確認を入れるか（チェックポイント）
    ↓
Step 3: 自動テスト実行
  Claude が Playwright MCP で自動テストを実行
    ↓
Step 4: チェックポイントでユーザー確認
  事前に決めたチェックポイントに到達したらユーザーに確認を依頼
    ↓
Step 5: 合格判定
  自動テスト全パス ＋ ユーザー確認OK → 合格
    ↓
Step 6: 次の機能の実装へ
```

## 2. 共通チェックテンプレート

すべての機能に適用する共通テスト項目。機能別合格基準（§3）と組み合わせて使用する。

### 2.1 UI操作系

| # | テスト項目 | 確認内容 |
|---|-----------|---------|
| U-01 | Undo/Redo | Ctrl+Z / Ctrl+Y で変更が正しく戻る・やり直せる |
| U-02 | モーダル開閉 | 開く→内容表示→閉じる（×ボタン・Esc・背景クリック） |
| U-03 | モーダル内操作 | 入力・選択・保存が正常に動作する |
| U-04 | テーマ切替 | ダーク/ライト切替後にレイアウト崩れがない |
| U-05 | キーボードショートカット | 定義済みショートカットが正常に機能する |
| U-06 | ドラッグ&ドロップ | 対象要素が正しく移動・並び替えされる |
| U-07 | 右クリックメニュー | コンテキストメニューが適切に表示・動作する |
| U-08 | ツールチップ | ホバーで適切な情報が表示される |

### 2.2 インタラクション連携系

動的に追加・変更された要素が、既存機能と正しく連携するかを検証する。

| # | テスト項目 | 確認内容 |
|---|-----------|---------|
| I-01 | 追加行の後続操作 | 新規追加した行に対して、既存行と同じ操作（モーダル・ホバー・D&D等）が正常に動作する |
| I-02 | data属性の引き継ぎ | 動的生成した要素が、静的HTMLの同等要素と同じdata属性セットを持っている |
| I-03 | モーダル間データ連携 | モーダルAで入力した値が、モーダルBで正しく読み取れる（コンボボックス・チップ・テキスト） |
| I-04 | フィルタ状態の反映 | グローバルなフィルタ・表示設定が、新規追加した要素にも正しく適用される |

### 2.3 データ系

| # | テスト項目 | 確認内容 |
|---|-----------|---------|
| D-01 | 入力バリデーション | 必須項目の空欄、型不一致、範囲外の値で適切なエラー表示 |
| D-02 | 保存 | データが正しく保存され、再読込後も維持される |
| D-03 | 削除 | 削除確認ダイアログ→削除→表示から消える |
| D-04 | 編集 | 既存データの変更が正しく反映される |
| D-05 | エラーハンドリング | 異常系（通信エラー等）で適切なメッセージ表示 |
| D-06 | データ整合性 | 画面間・モーダル間でデータが同期されている |
| D-07 | フィルタ・検索 | 条件に一致するデータのみ表示される |
| D-08 | ソート | 昇順・降順が正しく動作する |

### 2.4 表示系

| # | テスト項目 | 確認内容 |
|---|-----------|---------|
| V-01 | レスポンシブ | PC・タブレット・モバイルでレイアウト崩れがない |
| V-02 | アイコン表示 | SVGアイコンが正しく表示される（フォールバック含む） |
| V-03 | バッジ・タグ | カテゴリバッジ・チップが正しい色・テキストで表示 |
| V-04 | 空状態 | データがない場合に適切なメッセージが表示される |
| V-05 | ローディング | 読込中に適切なインジケータが表示される |
| V-06 | 通知・トースト | 操作結果のフィードバックが表示される |
| V-07 | スクロール | 大量データでスクロールが正常に機能する |
| V-08 | 印刷プレビュー | 印刷用レイアウトが正しく表示される（対象画面のみ） |

## 3. 機能別合格基準の導出ルール

### 3.1 導出の流れ

```text
1. 実装した機能を特定
2. 要件定義（01）から該当する機能要件を抽出
3. DB設計（03）から関連テーブル・制約を確認
4. モックアップの実装内容から操作パターンを洗い出す
5. 影響範囲分析（§3.3）を実施
6. 上記を統合してテスト項目を作成
7. 共通テンプレート（§2）から該当項目を選択
8. 機能固有 ＋ 共通 を合わせた合格基準としてユーザーに提示
```

### 3.2 テスト項目の記述形式（機能固有テスト）

各テスト項目は以下の形式で記述する。

```
[ID] テスト項目名
  操作: ユーザーが行う操作手順
  期待結果: 正常時に期待される状態
  合格条件: パスと判定する具体的な基準
```

### 3.3 影響範囲分析（Impact Analysis）

機能の実装・変更時に、追加・変更した要素が既存コードのどこから参照されるかを洗い出す。
これにより「追加して終わり」にならない後続操作のテスト項目を導出する。

#### 手順

```text
1. 追加・変更した要素（DOM要素・data属性・CSS クラス等）を列挙する
2. 既存コードでその要素を参照している関数・セレクタを検索する
   （querySelector, getAttribute, dataset, closest 等で grep）
3. 各関数が期待するDOM構造・data属性・クラスを一覧化する
4. 動的生成コード（cnCreateRow等）が、静的HTMLと同じ属性セットを
   出力しているか差分チェックする
5. 差分がある場合はテスト項目として追加、または実装を修正する
```

#### 具体例：スクリーンレイアウト「新規追加」

```text
追加要素: cnCreateRow() で生成した <tr> の .col-site-info セル

参照する既存関数:
  openSiteModal()    → data-group-company, data-gc-name, data-companyId,
                       .company テキスト, .site-name テキスト
  cnGetRowInfo()     → .category-badge, .shift-badge, .site-name
  extractGridData()  → .category-badge, .shift-badge, .company, .site-name
  CSS :hover::after  → data-gc-name (ツールチップ)

静的HTMLが持つ属性:
  data-group-company="touo" data-gc-name="東央警備"
  data-company-id="1" data-site-id="101"

→ cnCreateRow に不足していた data-group-company, data-gc-name を追加
→ openSiteModal に companiesData 未登録時のフォールバックを追加
```

### 3.4 例：受注簿の「受注追加」機能

```
[OB-001] 新規受注の追加
  操作: 追加ボタン押下 → 必須項目入力 → 保存
  期待結果: グリッドに新しい行が追加される
  合格条件: 追加後のグリッド行数が+1、入力値が正しく表示されている

[OB-002] 受注追加のバリデーション
  操作: 必須項目を空欄のまま保存を押下
  期待結果: エラーメッセージが表示され、保存されない
  合格条件: エラー表示あり、グリッド行数が変化していない
```

## 4. 合格判定基準

### 4.1 自動テスト（Claude実行）

| 判定 | 条件 |
|------|------|
| PASS | 期待結果と実際の結果が一致 |
| FAIL | 期待結果と実際の結果が不一致 |
| SKIP | 当該機能が未実装、またはテスト対象外 |
| BLOCKED | 前提条件が満たせずテスト実行不可 |

### 4.2 ユーザー確認

| 判定 | 条件 |
|------|------|
| OK | ユーザーが確認し、問題なし |
| NG | ユーザーが問題を指摘 → 修正後に再テスト |

### 4.3 総合合格条件

```
すべてのテスト項目が PASS または SKIP
 ＋
すべてのユーザー確認項目が OK
 → 合格（次の機能の実装へ進む）
```

FAIL または NG が1件でもある場合 → 修正後に該当項目を再テスト。

## 5. モックアップでの試運用ルール

Phase 2（モックアップ）では以下の制約のもと試運用する。

| 項目 | 本番（Phase 4） | 試運用（Phase 2） |
|------|-----------------|-------------------|
| データ系テスト | DB・API含む | モック内データのみ |
| レスポンシブ | 全ブレークポイント | PC表示のみ（対象画面を除く） |
| エラーハンドリング | 通信エラー等含む | UI上のバリデーションのみ |
| E2Eテスト | 画面間連携 | 単一画面内のみ |

試運用の目的は **テストフロー自体の検証と改善** であり、モックアップの品質保証は副次的な成果とする。

## 6. 改善ログ

試運用で得た知見・修正を記録する。各エントリは日付・対象・内容を含める。

| 日付 | 対象 | 種別 | 内容 |
| ------ | ------ | ------ | ------ |
| 2026-04-06 | 共通テンプレート | 追加 | §2.2「インタラクション連携系」(I-01〜I-04)を新設。動的生成要素と既存機能の連携テストが抜けていた |
| 2026-04-06 | 導出フロー | 追加 | §3.3「影響範囲分析」ステップを追加。追加した要素を参照する既存関数の洗い出しを義務化 |
| 2026-04-06 | screen-layout | 知見 | cnCreateRowでdata属性が不足→openSiteModalが空表示。動的生成関数は静的HTMLとの属性差分チェックが必須 |

### 種別の定義

- **追加**: テンプレートやフローに新しい項目・ステップを追加
- **変更**: 既存の項目・フローを修正
- **削除**: 不要と判断した項目・ステップを削除
- **知見**: プロセスに関する気づき・学び（変更は伴わない）
