# データベース設計書

## 1. 概要

### 1.1 データベース

- **DBMS**: PostgreSQL（Supabase）
- **文字コード**: UTF-8

### 1.2 設計方針

- 正規化を基本としつつ、パフォーマンスを考慮
- 拡張性を確保（将来の機能追加に対応）
- 履歴管理のためのタイムスタンプを全テーブルに設置
- フロントエンド非依存: React Webアプリ（先行開発）およびExcel VBA UI（後続開発）の両方からSupabase REST APIで共通利用
- 画面横断の単一情報源を優先: OB/SL/WS/LA など画面ごとのローカルコピーではなく、日毎受注・日毎配置・社員・車両・ETC・休暇申請の共通テーブルを参照する

## 3. テーブル定義

### 3.0 group_companies（グループ会社マスタ）

自社グループ会社（東央警備、Nikkeiホールディングス等）を管理するマスタ。
契約先（元請け先）とは異なり、自社側の所属会社を表す。
各現場（sites）はいずれかのグループ会社に紐付く。
**注文書の「甲（委託者）」情報ソースも兼ねる**（住所・代表者役職・代表者名・電話）。

| カラム名             | 型           | NULL | 説明                                           |
| -------------------- | ------------ | ---- | ---------------------------------------------- |
| id                   | UUID         | NO   | 主キー                                         |
| code                 | VARCHAR(20)  | NO   | グループ会社コード（ユニーク）                 |
| name                 | VARCHAR(100) | NO   | グループ会社名                                 |
| short_name           | VARCHAR(20)  | YES  | 表示用略称（例: 東央, Nikkei）                 |
| badge_color          | VARCHAR(7)   | YES  | ボーダー色（例: #93c5fd）                      |
| badge_text_color     | VARCHAR(7)   | YES  | バッジ文字色（例: #ffffff）                    |
| postal_code          | VARCHAR(8)   | YES  | 郵便番号（例: 780-0945）※注文書甲情報          |
| address              | TEXT         | YES  | 住所（都道府県から記載）※注文書甲情報          |
| representative_title | VARCHAR(50)  | YES  | 代表者役職（例: 代表取締役）※注文書甲情報      |
| representative_name  | VARCHAR(50)  | YES  | 代表者名（例: 藤田剛志）※注文書甲情報          |
| phone                | VARCHAR(20)  | YES  | 代表電話番号（例: 088-856-6666）※注文書甲情報  |
| sort_order           | INTEGER      | YES  | 表示順                                         |
| is_active            | BOOLEAN      | NO   | 有効フラグ（デフォルト: true）                 |
| created_at           | TIMESTAMPTZ  | NO   | 作成日時                                       |
| updated_at           | TIMESTAMPTZ  | NO   | 更新日時                                       |

```sql
CREATE TABLE group_companies (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    code VARCHAR(20) NOT NULL UNIQUE,
    name VARCHAR(100) NOT NULL,
    short_name VARCHAR(20),
    badge_color VARCHAR(7) DEFAULT '#718096',
    badge_text_color VARCHAR(7) DEFAULT '#ffffff',
    postal_code VARCHAR(8),
    address TEXT,
    representative_title VARCHAR(50),
    representative_name VARCHAR(50),
    phone VARCHAR(20),
    sort_order INTEGER DEFAULT 0,
    is_active BOOLEAN NOT NULL DEFAULT true,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

### 3.1 companies（契約先マスタ）

契約先（元請け先）マスタ。`name` はUI表示用の**略称**（例: `(株)○○`）、`formal_name` は**正式名称**（例: `株式会社○○`）で、注文書の「丙（発注者）」記載時に使用。受注簿・週間予定表等では `name` を表示し、注文書発行時にのみ `formal_name` を参照する。

※ `formal_name`: 略称→正式名称の変換規則は co-company-input.js の PATTERNS が正（(株)/(有)/(合)/(資)/(名)/(特非)/(一社)/(一財)/(公社)/(公財)/㈱㈲㈳㈶㈴㈾/NPO法人 等10種超を網羅）

| カラム名     | 型           | NULL | 説明                                                       |
| ------------ | ------------ | ---- | ---------------------------------------------------------- |
| id           | UUID         | NO   | 主キー                                                     |
| code         | VARCHAR(20)  | NO   | 契約先コード（ユニーク）                                   |
| name         | VARCHAR(100) | NO   | 契約先名（UI表示用略称）                                   |
| formal_name  | VARCHAR(200) | NO   | 正式名称（注文書用、括弧株等を展開）                       |
| notes        | TEXT         | YES  | 備考                                                       |
| sort_order   | INTEGER      | YES  | 表示順                                                     |
| is_active    | BOOLEAN      | NO   | 有効フラグ（デフォルト: true）                             |
| created_at   | TIMESTAMPTZ  | NO   | 作成日時                                                   |
| updated_at   | TIMESTAMPTZ  | NO   | 更新日時                                                   |

```sql
CREATE TABLE companies (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    code VARCHAR(20) NOT NULL UNIQUE,
    name VARCHAR(100) NOT NULL,
    formal_name VARCHAR(200) NOT NULL,
    notes TEXT,
    sort_order INTEGER DEFAULT 0,
    is_active BOOLEAN NOT NULL DEFAULT true,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- 曖昧検索用（Quick Access新規契約先登録時の重複防止バリデーション）
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_companies_name_trgm ON companies USING GIN (name gin_trgm_ops);
```

### 3.2.1 category_badges（区分バッジマスタ）

区分（site_categories）に紐づく子バッジの定義。
セル編集モーダルで区分に応じた子バッジをチップ選択できる。
親バッジ＝区分名（読み取り専用）、子バッジ＝本テーブルで定義された選択肢。

| カラム名        | 型           | NULL | 説明                                              |
| --------------- | ------------ | ---- | ------------------------------------------------- |
| id              | UUID         | NO   | 主キー                                            |
| category_id     | UUID         | NO   | 区分ID（FK）                                      |
| parent_badge_id | UUID         | YES  | 親バッジID（自己参照FK、NULLなら子バッジ）        |
| level           | INTEGER      | NO   | 階層レベル（1=子バッジ, 2=孫バッジ）              |
| code            | VARCHAR(20)  | NO   | バッジコード                                      |
| name            | VARCHAR(50)  | NO   | バッジ名（表示用）                                |
| color           | VARCHAR(7)   | YES  | バッジ背景色                                      |
| text_color      | VARCHAR(7)   | YES  | バッジ文字色                                      |
| sort_order      | INTEGER      | YES  | 表示順                                            |
| is_active       | BOOLEAN      | NO   | 有効フラグ                                        |
| created_at      | TIMESTAMPTZ  | NO   | 作成日時                                          |
| updated_at      | TIMESTAMPTZ  | NO   | 更新日時                                          |

※ 親バッジは `site_categories.name` をそのまま使用（読み取り専用表示）
※ 子バッジ: `parent_badge_id = NULL`, `level = 1`（区分直下）
※ 孫バッジ: `parent_badge_id = 子バッジID`, `level = 2`（子バッジの詳細項目）
※ 子バッジが0件の区分もある（施設、イベント等）。その場合、UIでは「バッジなし」と表示し、追加ボタンから新規作成可能
※ ユーザーがモーダルから新規バッジを追加した場合、本テーブルにINSERTされる

```sql
CREATE TABLE category_badges (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    category_id UUID NOT NULL REFERENCES site_categories(id) ON DELETE CASCADE,
    parent_badge_id UUID REFERENCES category_badges(id) ON DELETE CASCADE,
    level INTEGER NOT NULL DEFAULT 1 CHECK (level IN (1, 2)),
    code VARCHAR(20) NOT NULL,
    name VARCHAR(50) NOT NULL,
    color VARCHAR(7) DEFAULT '#718096',
    text_color VARCHAR(7) DEFAULT '#ffffff',
    sort_order INTEGER DEFAULT 0,
    is_active BOOLEAN NOT NULL DEFAULT true,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE(category_id, code)
);

CREATE INDEX idx_category_badges_category ON category_badges(category_id);
CREATE INDEX idx_category_badges_parent ON category_badges(parent_badge_id);

-- 初期データ（高速系）
INSERT INTO category_badges (category_id, code, name, sort_order)
SELECT sc.id, b.code, b.name, b.sort_order
FROM site_categories sc
CROSS JOIN (VALUES
    ('LANE_REGULATION', '車線規制', 1),
    ('SHOULDER_REGULATION', '路肩規制', 2),
    ('BOOTH_REGULATION', 'ブース規制', 3),
    ('SECURITY_GUARD', '保安員', 4)
) AS b(code, name, sort_order)
WHERE sc.code = 'HIGHWAY';

-- 初期データ（交通系）
INSERT INTO category_badges (category_id, code, name, sort_order)
SELECT sc.id, b.code, b.name, b.sort_order
FROM site_categories sc
CROSS JOIN (VALUES
    ('ALTERNATE_TRAFFIC', '片側交互', 1),
    ('ROAD_CLOSURE', '通行止め', 2)
) AS b(code, name, sort_order)
WHERE sc.code = 'TRAFFIC';

-- 孫バッジ（level=2、Mockup badgeDefinitions準拠）
-- 高速 → 車線規制 → 標識車/規制材/保安灯
INSERT INTO category_badges (category_id, parent_badge_id, level, code, name, sort_order)
SELECT pb.category_id, pb.id, 2, g.code, g.name, g.sort_order
FROM category_badges pb
CROSS JOIN (VALUES
    ('LANE_SIGN', '標識車', 1),
    ('LANE_MAT', '規制材', 2),
    ('LANE_LIGHT', '保安灯', 3)
) AS g(code, name, sort_order)
WHERE pb.code = 'LANE_REGULATION'
  AND pb.category_id = (SELECT id FROM site_categories WHERE code = 'HIGHWAY');

-- 高速 → 路肩規制 → コーン/バー
INSERT INTO category_badges (category_id, parent_badge_id, level, code, name, sort_order)
SELECT pb.category_id, pb.id, 2, g.code, g.name, g.sort_order
FROM category_badges pb
CROSS JOIN (VALUES
    ('SHOULDER_CONE', 'コーン', 1),
    ('SHOULDER_BAR', 'バー', 2)
) AS g(code, name, sort_order)
WHERE pb.code = 'SHOULDER_REGULATION'
  AND pb.category_id = (SELECT id FROM site_categories WHERE code = 'HIGHWAY');

-- 交通 → 片側交互 → 旗/看板
INSERT INTO category_badges (category_id, parent_badge_id, level, code, name, sort_order)
SELECT pb.category_id, pb.id, 2, g.code, g.name, g.sort_order
FROM category_badges pb
CROSS JOIN (VALUES
    ('ALT_FLAG', '旗', 1),
    ('ALT_SIGN', '看板', 2)
) AS g(code, name, sort_order)
WHERE pb.code = 'ALTERNATE_TRAFFIC'
  AND pb.category_id = (SELECT id FROM site_categories WHERE code = 'TRAFFIC');
```

```sql
VALUES
    ((SELECT id FROM nikkei), NULL, (SELECT id FROM lt_section), 'FACILITY', '施設課', 1),
    ((SELECT id FROM nikkei), NULL, (SELECT id FROM lt_section), 'TRAFFIC', '交通課', 2);

-- 全日本エンタープライズ: 拠点→課の2階層
WITH zen AS (SELECT id FROM group_companies WHERE code = 'ZENNIHON'),
     lt_base AS (SELECT id FROM org_level_types WHERE group_company_id = (SELECT id FROM zen) AND depth = 1)
INSERT INTO organization_units (group_company_id, parent_id, level_type_id, code, name, sort_order)
VALUES
    ((SELECT id FROM zen), NULL, (SELECT id FROM lt_base), 'HONSHA', '本社', 1),
    ((SELECT id FROM zen), NULL, (SELECT id FROM lt_base), 'EHIME', '愛媛営業所', 2);

-- 本社の下に課を追加
WITH zen AS (SELECT id FROM group_companies WHERE code = 'ZENNIHON'),
     honsha AS (SELECT id FROM organization_units WHERE code = 'HONSHA' AND group_company_id = (SELECT id FROM zen)),
     lt_section AS (SELECT id FROM org_level_types WHERE group_company_id = (SELECT id FROM zen) AND depth = 2)

WITH RECURSIVE tree AS (
    SELECT id, group_company_id, parent_id, level_type_id, code, name, sort_order, is_active,
           id AS root_id, 1 AS tree_depth, ARRAY[id] AS path
    FROM organization_units
    WHERE parent_id IS NULL
    UNION ALL
    SELECT ou.id, ou.group_company_id, ou.parent_id, ou.level_type_id, ou.code, ou.name, ou.sort_order, ou.is_active,
           tree.root_id, tree.tree_depth + 1, tree.path || ou.id
    FROM organization_units ou
    JOIN tree ON ou.parent_id = tree.id
)
SELECT t.*, olt.name AS level_type_name, olt.depth AS level_depth
FROM tree t
JOIN org_level_types olt ON t.level_type_id = olt.id;
```

### 3.6 daily_site_orders（日毎受注）

OB（受注簿）/ QA（受注クイック入力）/ SL（業務管理計画書の行追加・受注メタ編集）から作成・更新される日毎受注情報を管理するテーブル。
「どの現場に、いつ、何名必要か」という受注の基本情報を保持する。

**業務背景**: 受注情報の業務上の起点はOB/QAであり、SLは選択日付の `daily_site_orders` を参照して配置表を描画する。ただし、現行MockupではSL上でも受注行追加・行メタ編集・行削除を行えるため、これらも同じ `daily_site_orders` への作成・更新として扱う。営業担当者が直接入力できない場合は、
配置担当者がSL/OBから代理入力する。複数ユーザーが同じ受注情報を変更する可能性があるため、
変更履歴の記録と楽観的ロックによる競合検知が必要。

| カラム名        | 型           | NULL | 説明                                                        |
| --------------- | ------------ | ---- | ----------------------------------------------------------- |
| id              | UUID         | NO   | 主キー                                                      |
| order_date      | DATE         | NO   | 受注対象日                                                  |

| group_company_id | UUID        | YES  | 受注を担当する自社グループ会社（FK → group_companies）。Mockupの受注行 branch（東央警備/Nikkeiホールディングス/全日本エンタープライズ）に相当し group_companies.code（touo/nikkei/zennihon）でマッピング。OB/SLのGC別表示・印刷分けの起点 |
| shift_type      | VARCHAR(10)  | NO   | シフト区分（day/night）                                     |
| placement_seq   | INTEGER      | NO   | 配置先連番（デフォルト: 0、同一行の複数配置先を区別）       |
| required_count  | INTEGER      | NO   | 必要人数                                                    |
| start_time      | TIME         | YES  | 開始時間                                                    |
| end_time        | TIME         | YES  | 終了時間                                                    |
| supervisor_name | VARCHAR(100) | YES  | 現場監督名                                                  |
| supervisor_tel  | VARCHAR(20)  | YES  | 現場監督連絡先                                              |
| meeting_place   | VARCHAR(100) | YES  | 集合場所                                                    |

| daily_task_name | VARCHAR(200) | YES  | 計画書業務名（自動生成: 親業務名 > 子 > 孫）                |

| auto_generation_type | VARCHAR(30) | YES | 自動生成種別（intergroup_support等）                       |
| source_order_id | UUID         | YES  | 自動生成元の日毎受注ID（FK → daily_site_orders）            |
| source_employee_id | UUID      | YES  | 自動生成トリガーとなった配置社員ID（FK → employees）        |

※ `badge_gc_map`: 選択された孫バッジのマップ。キーは子バッジID、値は孫バッジID配列。例: `{"hw-lane": ["hw-lane-sign", "hw-lane-mat"]}`
※ `confidence`: 信頼度。confirmed=確定、tentative_high=予定（信頼:高）、tentative_low=予定（信頼:低）。新規入力時のデフォルトはtentative_high
※ `confidence` 自動確定ルール: (1) 受注対象日（order_date）が昨日以前 → 自動的にconfirmedに変更。(2) 業務管理計画書（daily_assignments）で社員が配置された場合 → 自動的にconfirmedに変更
※ Mockupデモ実装では新規/生成セルに confirmed を用いる箇所があるが、正規のデフォルト値は要確定（Phase 2.5判断）。本書のデフォルト tentative_high は据え置き
※ `confidence_manual`: 確度を手動確定したかのフラグ。自動確定ルールの上書き制御に使用（Mockup: confidenceManual）
※ `group_company_id`: 受注を担当する自社グループ会社。Mockupの受注行 branch（東央警備/Nikkeiホールディングス/全日本エンタープライズ）に相当し group_companies.code（touo/nikkei/zennihon）でマッピング。OB/SLのGC別表示・印刷分けの起点
※ `maps`: Mockupは新形式 `maps`(配列) と旧形式 `mapUrl`(単一文字列) を併用し読込はmaps優先・mapUrlフォールバック。`mapUrl`はレガシーで `maps` 配列が正
※ OBの行情報編集は presetStartTime/presetEndTime（行レベル既定開始/終了時刻）を保持し、新規セルの start_time/end_time の既定値に使う。格納先は同一 site_id+業務 単位の行テンプレートとし本実装フェーズで確定（Mockup未確定）
※ Mockupのセルは表示用に配置社員名(`assignment`)を保持するが、これはOB単独表示用であり本来は assignment_details 由来。daily_site_orders には配置社員を持たせない
※ `status`: active=有効、cancelled=その日のキャンセル
※ `is_auto_generated`: SLで他GC所属社員を配置した場合など、システムが自動作成した受注行を示す。OBでは完全ロック表示とし、編集・削除は生成元配置の変更に同期する
※ `source_order_id` / `source_employee_id`: グループ間応援の自動生成行で、生成元の受注と社員を追跡する。DB上は生成元受注+社員の組を追跡できる粒度で保持し、OB表示では同一区分・昼夜・契約先名・業務名の自動生成受注を1行へ集約表示してよい
※ `version`: 楽観的ロック用。保存時にバージョンを照合し、他者が先に変更していた場合は警告を表示
※ `placement_seq`: 同一日・同一現場・同一シフトで複数の配置先に分けるための連番。通常は0。複数配置先の場合は0, 1, 2...と増加
※ `created_by` / `updated_by`: 誰が入力・変更したかを記録

### 3.7.2 order_change_history（受注変更履歴）

日毎受注（daily_site_orders）の全変更を記録するテーブル。変更されたカラム名・変更前の値・変更後の値を記録し、
任意の過去バージョンへのロールバックを可能にする。

**業務背景**: 複数の営業担当者が受注情報を入力・変更し、配置担当者が代理入力やキャンセル処理を行う運用において、
聞き間違いによる誤キャンセル、誤った人数変更、他の営業担当者による誤情報の上書きが発生する。
変更履歴により「誰がいつ何を変更したか」を追跡し、誤操作時のロールバックを可能にする。

| カラム名       | 型           | NULL | 説明                                                |
| -------------- | ------------ | ---- | --------------------------------------------------- |
| id             | UUID         | NO   | 主キー                                              |
| order_id       | UUID         | NO   | 日毎受注ID（FK）                                    |
| version        | INTEGER      | NO   | この変更後のバージョン番号                          |
| operation_type | VARCHAR(20)  | NO   | 操作種別（create/update/cancel/restore/rollback/merge） |
| changed_fields | JSONB        | NO   | 変更内容 [{field, old_value, new_value}, ...]       |
| change_reason  | TEXT         | YES  | 変更理由（任意入力）                                |
| changed_by     | UUID         | NO   | 変更者（FK → employees）                            |
| changed_at     | TIMESTAMPTZ  | NO   | 変更日時                                            |

**operation_type の値**:

| 値       | 説明                                               |
| -------- | -------------------------------------------------- |
| create   | 新規受注の入力                                     |
| update   | 通常の更新（人数変更、時間変更等）                 |
| cancel   | その日のキャンセル処理（status → cancelled）       |
| restore  | キャンセルからの復元（status → active）            |
| rollback | 過去バージョンへのロールバック                     |
| merge    | 競合解決時のスマートマージ（非重複項目の統合）     |

※ cancel/restore/rollback/merge は仕様先行（Mockup未実装）。現Mockupが扱う操作は row/site の modify・delete、badge の add/delete のみ。status(active/cancelled)を切替えるキャンセルUIもOB Mockup未実装

**changed_fields の形式**:

```json
[
  { "field": "required_count", "old_value": "3", "new_value": "2" },
  { "field": "start_time", "old_value": "08:00", "new_value": "09:00" },
  { "field": "status", "old_value": "active", "new_value": "cancelled" }
]
```

```sql
CREATE TABLE order_change_history (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    order_id UUID NOT NULL REFERENCES daily_site_orders(id) ON DELETE CASCADE,
    version INTEGER NOT NULL,
    operation_type VARCHAR(20) NOT NULL CHECK (operation_type IN ('create', 'update', 'cancel', 'restore', 'rollback', 'merge')),
    changed_fields JSONB NOT NULL DEFAULT '[]'::jsonb,
    change_reason TEXT,
    changed_by UUID NOT NULL REFERENCES employees(id),
    changed_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE(order_id, version)
);

CREATE INDEX idx_order_change_history_order ON order_change_history(order_id);
CREATE INDEX idx_order_change_history_changed_by ON order_change_history(changed_by);
CREATE INDEX idx_order_change_history_changed_at ON order_change_history(changed_at);
```

**リアルタイム同期との関係**:

受注簿と業務管理計画書は同一DBを共有し、Supabase Realtimeによりデータ変更は全画面にリアルタイム反映される。自分・他ユーザーの変更ともに変更通知モーダルで確認でき、「元に戻す」「やっぱり反映」で操作可能（全ユーザー使用可）。復元には通知レコードに保存された変更前後のスナップショット（`snapshot_before` / `snapshot_after`）を使用する。

**楽観的ロック（競合検知）の動作**:

1. 画面表示時に受注の `version` を取得
2. 保存時にDBの `version` と照合
3. 一致すれば保存成功 → `version` をインクリメント、`order_change_history` に記録
4. 不一致なら他者が先に変更済み → **スマートマージ判定**を実行（下記参照）

**スマートマージ（競合解決）の動作**:

バージョン不一致を検知した場合、自分の変更項目と他者の変更項目を比較し、競合の種類に応じた解決方法を提示する。

**ケースA: 変更項目が重複しない場合（自動マージ候補）**
- 例: 営業Aが `start_time` を変更、営業Bが `required_count` を変更
- ダイアログで両者の変更内容を表示し、以下の選択肢を提示:
  - **両方の変更をマージ**: 営業Aの変更と営業Bの変更を統合して保存（`operation_type = 'merge'`）
  - **自分の変更のみ上書き**: 他者の変更を破棄し、自分の変更で上書き
  - **キャンセル**: 保存を中止し、最新データを再取得

**ケースB: 変更項目が重複する場合（手動選択必須）**
- 例: 営業Aも営業Bも `required_count` を変更
- 競合ダイアログで重複項目ごとに以下を表示:
  - 変更前の値（ベースバージョン）
  - 他者の変更後の値（現在のDB値）
  - 自分の変更後の値
- 各項目について、他者の値と自分の値のどちらを採用するか選択
- 非重複項目がある場合は、それらも含めてマージ
- 最終的な変更内容を確認後に保存（`operation_type = 'merge'`）

**マージ後の履歴記録**:
- マージ操作は `operation_type = 'merge'` として `order_change_history` に記録
- `changed_fields` には最終的に適用された変更の差分を記録
- `change_reason` に「バージョンX（営業Aの変更）とマージ」等の自動メモを付与

**ロールバックの動作**:

1. 変更履歴一覧からロールバック先のバージョンを選択
2. 選択バージョンの `changed_fields` から、そのバージョン時点の値を復元
3. ロールバック自体も `operation_type = 'rollback'` として履歴に記録
4. 営業担当者・配置担当者・管理者がロールバック可能

### 3.9 連続勤務（自動検知）

連続勤務はテーブルで管理せず、**配置データから自動検知**する機能として実装。

#### 検知ロジック

**検知範囲**: 同日内 + 日をまたぐパターンの両方

Mockup実装は当日配置を基準に2軸（▼上＝前方連結 / ▼下＝後方連結）の2フラグのみで判定する。

| 軸           | 説明                               | 検知条件                                                   |
| ------------ | ---------------------------------- | ---------------------------------------------------------- |
| ▼上（前方連結） | 前日夜→当日昼 等の直前との繋がり | 同一社員が前日夜に配置（夜配置時は同日昼の配置）           |
| ▼下（後方連結） | 当日昼→当日夜 等の直後への繋がり | 同一社員が同日夜に配置                                     |

※ 翌日昼方向（『昼→夜→昼』）の3連勤検知は仕様先行（Mockup未実装）。Mockupは ▼上/▼下 の2軸のみで、翌日昼方向は未検知

#### 表示方法

- **アイコン・バッジ**: 連続勤務パターンを示すアイコンを社員名の横に表示
- **背景色**: 連続勤務中の社員を背景色で視覚的に強調

#### モックアップ実装との対応（業務管理計画書 ▼ マーク）

業務管理計画書グリッドでは、配置済み社員名の **上下に ▼ マーク** を表示する形で連勤を視覚化する。判定ルールは要件定義 [3.3.3 連続勤務管理](01_要件定義.md#333-連続勤務管理) に整理：

| 当日配置 | ▼上 マーク（直前との繋がり） | ▼下 マーク（直後への繋がり） |
| ---- | ---- | ---- |
| 昼配置 | 前日 `daily_site_orders.shift_type='night'` の配置あり | 同日 `daily_site_orders.shift_type='night'` の配置あり（同一社員） |
| 夜配置 | 同日 `daily_site_orders.shift_type='day'` の配置あり（同一社員） | （常に無し） |

**配置・移動・解除のたびに全行を再判定**するため、SQL は (1) `assignment_details` → `daily_assignments` → `daily_site_orders` を結合して当日配置を employee_id で集計、(2) 前日夜勤の存在を `EXISTS` で確認、の2クエリで導出可能（上記 SQL 例を流用）。モックアップでは `employees.workedPrevNight` フラグでデモしているが、実装時は前日 `daily_site_orders` + `daily_assignments` 参照に置き換える（フラグはマスタに保持しない）。

#### 検知SQL例

```sql
-- 特定日の社員の連続勤務パターンを検知
WITH employee_shifts AS (
    SELECT
        ad.employee_id,
        dso.order_date AS assignment_date,
        dso.shift_type,
        da.id as assignment_id
    FROM assignment_details ad
    JOIN daily_assignments da ON ad.daily_assignment_id = da.id
    JOIN daily_site_orders dso ON da.daily_site_order_id = dso.id
    WHERE dso.order_date BETWEEN :target_date - 1 AND :target_date
),
patterns AS (
    SELECT
        e1.employee_id,
        -- 同日の昼→夜
        CASE WHEN EXISTS (
            SELECT 1 FROM employee_shifts e2
            WHERE e2.employee_id = e1.employee_id
            AND e2.assignment_date = e1.assignment_date
            AND e1.shift_type = 'day' AND e2.shift_type = 'night'
        ) THEN true ELSE false END as day_to_night,
        -- 前日夜→当日昼
        CASE WHEN EXISTS (
            SELECT 1 FROM employee_shifts e2
            WHERE e2.employee_id = e1.employee_id
            AND e2.assignment_date = e1.assignment_date - 1
            AND e2.shift_type = 'night' AND e1.shift_type = 'day'
        ) THEN true ELSE false END as night_to_day
    FROM employee_shifts e1
    WHERE e1.assignment_date = :target_date
)
SELECT
    employee_id,
    CASE
        WHEN day_to_night AND night_to_day THEN 'night_day_night'
        WHEN day_to_night THEN 'day_to_night'
        WHEN night_to_day THEN 'night_to_day'
        ELSE null
    END as continuous_pattern
FROM patterns
WHERE day_to_night OR night_to_day;
```

### 3.9.1 業務管理計画書 固定3行の永続化方針

業務管理計画書グリッド末尾に常駐する3固定行（要件定義 [3.2.4](01_要件定義.md#324-固定行会社--休み申請なし-休み申請あり)）の DB 表現方針：

| 固定行 | 永続化方法 | 補足 |
| ---- | ---- | ---- |
| 会社 | `daily_site_orders` に **`category=COMPANY`（site_categories.code='COMPANY'）の特殊行**として永続化 | 当日「会社待機」社員は通常の `daily_assignments` で配置。site_id は会社待機専用の擬似 site を1件用意（GC ごとに）するか、site_id を NULL 許容化して category 単独で識別する案がある（実装時に確定） |
| 休み（申請なし） | **永続化しない**（純粋な UI 描画） | 印刷帳票の確認欄として常時表示。データソースなし |
| 休み（申請あり） | **`leave_requests`（3.22）から導出** | 当日 `leave_date = order_date` かつ `status='approved'` の社員を `slRenderHolidayRow()` 相当のロジックで動的描画。配置済みかは `daily_assignments` を逆引きして判定 |

**実装注意:**

- 「会社」行への配置は通常の `daily_assignments` レコードとして保存される。`daily_site_orders.required_count` は 0 でも良い（待機人数は導出可能）
- 「休み（申請あり）」行のドロップは無効。源泉は休暇申請管理画面（要件定義 3.17）からのみ
- 「休み（申請なし）」固定行は画面では `display:none` で非表示、印刷では表示。DB 操作は不要

| target_date           | DATE         | YES  | 業務上の対象日。日別表示・期間検索の基準。行全体・マスタ等で特定日を持たない通知はNULL |
| target_date_end       | DATE         | YES  | 対象期間の終端。単日の場合はNULL |
| company_id            | UUID         | YES  | 契約先（FK → companies）。契約先別検索用 |
| site_id               | UUID         | YES  | 現場（FK → sites）。現場別検索用 |
| daily_site_order_id   | UUID         | YES  | 日毎受注（FK → daily_site_orders） |
| daily_assignment_id   | UUID         | YES  | 日毎配置（FK → daily_assignments） |
| leave_request_id      | UUID         | YES  | 休暇申請（FK → leave_requests） |
| related_table         | VARCHAR(50)  | YES  | 上記以外の主対象テーブル名（マスタ通知等） |
| related_id            | UUID         | YES  | 上記以外の主対象レコードID |
| source_page           | VARCHAR(30)  | NO   | 操作元画面。カテゴリ導出には使用しない |
| primary_page          | VARCHAR(30)  | NO   | 「現場画面で開く」の第一着地画面 |
| targets               | JSONB        | NO   | 画面別ジャンプ先 `{ "order-book": {axis,value,date}, ... }` |
| affects               | TEXT[]       | NO   | 影響画面IDの配列 |
| summary               | TEXT         | NO   | 通知カードに表示する要約 |
| diffs                 | JSONB        | NO   | 変更差分 `[{field, old, new}]` |
| change_reason         | TEXT         | YES  | 業務判断理由・補足（任意） |
| snapshot_before       | JSONB        | YES  | 「元に戻す」用の変更前スナップショット |
| snapshot_after        | JSONB        | YES  | 「やっぱり反映」用の変更後スナップショット |
| revert_status         | VARCHAR(20)  | YES  | 復元状態（reverted/reapplied） |
| changed_by            | UUID         | NO   | 入力者・操作者（FK → employees） |
| created_at            | TIMESTAMPTZ  | NO   | システム入力日時 |
| updated_at            | TIMESTAMPTZ  | NO   | 復元状態等の最終更新日時 |

**カテゴリ導出ルール**:

| `domain` | 導出カテゴリ |
| -------- | ------------ |
| order | 受注 |
| person-assignment / vehicle-assignment / support-reservation | 配置 |
| leave | 申請・承認 |
| master | マスタ |

`assignment_subtag` は配置カテゴリだけに設定する。`vehicle-assignment` は `vehicle`、`support-reservation` は業務内容に応じて `support` または `partner`、自社社員配置は `own` とする。

```sql
CREATE TABLE change_notifications (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    domain VARCHAR(30) NOT NULL CHECK (domain IN (
        'order', 'person-assignment', 'vehicle-assignment',
        'support-reservation', 'leave', 'master'
    )),
    assignment_subtag VARCHAR(20) CHECK (assignment_subtag IN ('own', 'support', 'partner', 'vehicle')),
    scope VARCHAR(30) NOT NULL,
    operation_type VARCHAR(20) NOT NULL CHECK (operation_type IN (
        'add', 'modify', 'delete', 'place', 'approve', 'reject',
        'remove', 'revert', 'reapply'
    )),
    input_type VARCHAR(30) NOT NULL CHECK (input_type IN ('received_record', 'business_decision', 'system')),
    route_type VARCHAR(30) CHECK (route_type IN ('site_order', 'sales_contact', 'client_contact', 'business_judgment')),
    target_date DATE,
    target_date_end DATE,
    company_id UUID REFERENCES companies(id),
    site_id UUID REFERENCES sites(id),
    daily_site_order_id UUID REFERENCES daily_site_orders(id) ON DELETE SET NULL,
    daily_assignment_id UUID REFERENCES daily_assignments(id) ON DELETE SET NULL,
    leave_request_id UUID REFERENCES leave_requests(id) ON DELETE SET NULL,
    related_table VARCHAR(50),
    related_id UUID,
    source_page VARCHAR(30) NOT NULL,
    primary_page VARCHAR(30) NOT NULL,
    targets JSONB NOT NULL DEFAULT '{}'::jsonb,
    affects TEXT[] NOT NULL DEFAULT '{}'::text[],
    summary TEXT NOT NULL,
    diffs JSONB NOT NULL DEFAULT '[]'::jsonb,
    change_reason TEXT,
    snapshot_before JSONB,
    snapshot_after JSONB,
    revert_status VARCHAR(20) CHECK (revert_status IN ('reverted', 'reapplied')),
    changed_by UUID NOT NULL REFERENCES employees(id),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CHECK (target_date_end IS NULL OR (target_date IS NOT NULL AND target_date_end >= target_date)),
    CHECK (
        (domain IN ('person-assignment', 'vehicle-assignment', 'support-reservation') AND assignment_subtag IS NOT NULL)
        OR
        (domain NOT IN ('person-assignment', 'vehicle-assignment', 'support-reservation') AND assignment_subtag IS NULL)
    )
);

CREATE INDEX idx_change_notifications_target_date ON change_notifications(target_date DESC);
CREATE INDEX idx_change_notifications_domain_date ON change_notifications(domain, target_date DESC);
CREATE INDEX idx_change_notifications_assignment_subtag ON change_notifications(assignment_subtag, target_date DESC)
    WHERE assignment_subtag IS NOT NULL;
CREATE INDEX idx_change_notifications_site_date ON change_notifications(site_id, target_date DESC)
    WHERE site_id IS NOT NULL;
CREATE INDEX idx_change_notifications_company_date ON change_notifications(company_id, target_date DESC)
    WHERE company_id IS NOT NULL;
CREATE INDEX idx_change_notifications_changed_by ON change_notifications(changed_by, created_at DESC);
CREATE INDEX idx_change_notifications_targets ON change_notifications USING GIN (targets);
CREATE INDEX idx_change_notifications_affects ON change_notifications USING GIN (affects);
```

※ `target_date` は必ず設定し、週間等の範囲通知だけ `target_date_end` を併用する。日別グルーピングは範囲の開始日である `target_date` を基準とする。
※ `related_table` / `related_id` は多種のマスタ通知を扱うための補助参照。主要業務エンティティは明示FKを優先する。
※ 通知レコードは変更履歴そのものではない。業務データの監査正本は `order_change_history` / `change_history`、通知は表示・ジャンプ・復元操作に必要なスナップショットを保持する。

### 3.24 support_reservations（協力業者予約）

応援予約として事前交渉した協力業者の日別人数を保持する。
週間予定表の応援予約行に「残3」のように表示され、現場セルへの配置で残数が消費される（`support_assignments` と組み合わせて残数を算出）。

**シフト統一方針**: 予約段階では昼/夜の区分を持たず、`flex`（フレックス）に統一する。実際の昼/夜確定は現場セルへの配置時に `support_assignments.shift_type` で決まる（運用者が昼セル／夜セルのどちらへドロップするかで判定）。

| カラム名        | 型          | NULL | 説明                                            |
| --------------- | ----------- | ---- | ----------------------------------------------- |
| id              | UUID        | NO   | 主キー                                          |
| partner_id      | UUID        | NO   | 協力業者ID（support_partners FK）               |
| reserved_date   | DATE        | NO   | 予約対象日                                      |
| shift_type      | VARCHAR(10) | NO   | シフト種別（`flex` のみ）                       |
| reserved_count  | INTEGER     | NO   | 予約人数（下限0、上限なし）                     |
| notes           | TEXT        | YES  | 備考                                            |
| created_at      | TIMESTAMPTZ | NO   | 作成日時                                        |
| updated_at      | TIMESTAMPTZ | NO   | 更新日時                                        |

※ `shift_type`: 現行運用は `flex`（昼夜区分なし）のみ。将来的に昼専用／夜専用の予約が必要になった際に `day`/`night` を再開放できるよう列自体は残す。
※ 同一（partner_id, reserved_date, shift_type）に対して UNIQUE。現状は `shift_type='flex'` のみのため、実質（partner_id, reserved_date）のユニーク性と等価。
※ 残数 = `reserved_count` − 当該 partner/date の `support_assignments.assigned_count` 合計（昼夜合算）

```sql
CREATE TABLE support_reservations (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    partner_id UUID NOT NULL REFERENCES support_partners(id) ON DELETE CASCADE,
    reserved_date DATE NOT NULL,
    shift_type VARCHAR(10) NOT NULL DEFAULT 'flex' CHECK (shift_type IN ('flex')),
    reserved_count INTEGER NOT NULL DEFAULT 0 CHECK (reserved_count >= 0),
    notes TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE(partner_id, reserved_date, shift_type)
);

CREATE INDEX idx_support_reservations_date ON support_reservations(reserved_date);
CREATE INDEX idx_support_reservations_partner ON support_reservations(partner_id);
```

### 3.25 support_assignments（協力業者配置）

応援予約行から現場セルへD&D配置した結果を記録する。
`support_reservations` の予約残から消費される。配置先は現場マスタ（sites）ではなく、日付・シフト・配置先連番まで確定した `daily_site_orders` とする。同一（partner_id, 日毎受注, 消費元シフト）に対して複数人配置可（`assigned_count` で表現）。

| カラム名          | 型          | NULL | 説明                                                          |
| ----------------- | ----------- | ---- | ------------------------------------------------------------- |
| id                | UUID        | NO   | 主キー                                                        |
| partner_id        | UUID        | NO   | 協力業者ID（support_partners FK）                             |
| assigned_date     | DATE        | NO   | 配置日                                                        |
| shift_type        | VARCHAR(10) | NO   | 配置シフト（day/night）※flex予約を消費した場合も配置側は確定  |
| source_shift_type | VARCHAR(10) | NO   | 消費元予約シフト（day/night/flex）                            |
| daily_site_order_id | UUID      | NO   | 配置先の日毎受注ID（daily_site_orders FK）                    |
| assigned_count    | INTEGER     | NO   | 配置人数（同セル複数配置対応。デフォルト1）                   |
| created_at        | TIMESTAMPTZ | NO   | 作成日時                                                      |
| updated_at        | TIMESTAMPTZ | NO   | 更新日時                                                      |

※ `shift_type` は配置セル側のシフト（`day`/`night`）。flex予約を昼セルへ配置した場合は `shift_type='day'`, `source_shift_type='flex'`
※ `source_shift_type` は消費元予約のシフト種別。予約はフレックス統一のため現状 `flex` のみを許容（将来昼/夜専用予約を再開放した場合に拡張可）
※ `assigned_date` / `shift_type` は `daily_site_orders` から導出可能だが、予約残数集計・週表示を高速化するため冗長保持する。保存時は参照先 `daily_site_orders.order_date` / `shift_type` と一致することをアプリケーション層で検証する
※ D&D運用ルール: 同日内は別行・別シフトへ自由移動可、別日移動は同シフト維持（昼→昼／夜→夜）のみ。違反時はトーストで通知・移動キャンセル（3.18.14.2 参照）

```sql
CREATE TABLE support_assignments (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    partner_id UUID NOT NULL REFERENCES support_partners(id) ON DELETE CASCADE,
    assigned_date DATE NOT NULL,
    shift_type VARCHAR(10) NOT NULL CHECK (shift_type IN ('day', 'night')),
    source_shift_type VARCHAR(10) NOT NULL DEFAULT 'flex' CHECK (source_shift_type IN ('flex')),
    daily_site_order_id UUID NOT NULL REFERENCES daily_site_orders(id) ON DELETE CASCADE,
    assigned_count INTEGER NOT NULL DEFAULT 1 CHECK (assigned_count > 0),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_support_assignments_date ON support_assignments(assigned_date);
CREATE INDEX idx_support_assignments_partner ON support_assignments(partner_id);
CREATE INDEX idx_support_assignments_order ON support_assignments(daily_site_order_id);
```

### 3.31 user_profiles（ユーザープロフィール・ロール）

Supabase Auth のユーザー（`auth.users`）と業務データを繋ぐプロフィール。ロールベースアクセス制御（要件 §3.11）とアカウント画面（要件 §3.22）のユーザー管理タブの基盤（2026-07-11 採用）。

| カラム名          | 型          | NULL | 説明 |

| user_id           | UUID        | NO   | ユーザー（FK → auth.users、1:1） |
| employee_id       | UUID        | YES  | 紐付く社員（FK → employees） |
| group_company_id  | UUID        | YES  | 所属グループ会社（FK → group_companies）。employee_id があれば社員側を正とする |
| display_name      | VARCHAR(50) | NO   | 表示名（ナビの `.menu-user` 表示） |
| role              | VARCHAR(30) | NO   | ロール（sales=営業担当者 / dispatch=配置担当者 / accounting=経理 / admin=管理者）。語彙の最終確定は本実装時（要件 §3.11） |
| is_active         | BOOLEAN     | NO   | 有効フラグ（アカウント無効化） |
| created_at        | TIMESTAMPTZ | NO   | 作成日時 |
| updated_at        | TIMESTAMPTZ | NO   | 更新日時 |

```sql
CREATE TABLE user_profiles (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE UNIQUE,
    employee_id UUID REFERENCES employees(id),
    group_company_id UUID REFERENCES group_companies(id),
    display_name VARCHAR(50) NOT NULL,
    role VARCHAR(30) NOT NULL CHECK (role IN ('sales', 'dispatch', 'accounting', 'admin')),

    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()

CREATE INDEX idx_user_profiles_employee ON user_profiles(employee_id) WHERE employee_id IS NOT NULL;
```

### 3.32 user_preferences（ユーザー個人設定）

アカウント画面（要件 §3.22）の個人設定を key-value で保持し、ログイン時に復元する（2026-07-11 採用）。

| カラム名   | 型           | NULL | 説明 |
| ---------- | ------------ | ---- | ---- |
| id         | UUID         | NO   | 主キー |

```sql
    pref_value JSONB NOT NULL,
```

## 5. RLS（Row Level Security）ポリシー

Supabaseで認証されたユーザーのみアクセス可能にする設定。

```sql
-- 全テーブルにRLSを有効化
ALTER TABLE companies ENABLE ROW LEVEL SECURITY;
ALTER TABLE sites ENABLE ROW LEVEL SECURITY;
ALTER TABLE employees ENABLE ROW LEVEL SECURITY;
ALTER TABLE change_notifications ENABLE ROW LEVEL SECURITY;
ALTER TABLE route_participants ENABLE ROW LEVEL SECURITY;
ALTER TABLE notification_logs ENABLE ROW LEVEL SECURITY;
ALTER TABLE notification_reads ENABLE ROW LEVEL SECURITY;
ALTER TABLE user_profiles ENABLE ROW LEVEL SECURITY;
ALTER TABLE user_preferences ENABLE ROW LEVEL SECURITY;
-- ... 他のテーブルも同様

-- 認証済みユーザーは全データにアクセス可能（社内システムのため）
CREATE POLICY "Authenticated users can read all data" ON companies
    FOR SELECT USING (auth.role() = 'authenticated');

CREATE POLICY "Authenticated users can insert data" ON companies
    FOR INSERT WITH CHECK (auth.role() = 'authenticated');

CREATE POLICY "Authenticated users can update data" ON companies
    FOR UPDATE USING (auth.role() = 'authenticated');

-- ... 他のテーブルも同様
```
